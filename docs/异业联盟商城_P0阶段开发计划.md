# 异业联盟商城 · P0 阶段开发计划

> 依据：PRD v0.2、技术方案与数据模型 v1.0、`contracts/p0-api.yaml`、`AGENTS.md`
> 原则：契约先行、资金路径优先、每个里程碑可演示、可回滚。

## 1. 当前基线

| 项 | 状态 |
|---|---|
| 后端栈 | Django 4.2 LTS + DRF + SimpleJWT，模块化单体 |
| 数据模型 | 复式记账、订单状态机、结算项、商品模板与素材库已落地，迁移齐全 |
| 接口契约 | `p0-api.yaml`：76 个路径 / 92 个操作；生成快照 127 个 schema |
| 质量门禁 | `make verify`：ruff、django check、迁移一致性、契约校验、149 个测试、覆盖率 92.90% |
| 平台后台 | `/admin` 已注册全部表；支付配置、地址、购物车已建模 |
| 未完成 | 真实微信支付/退款、短信服务商、MySQL 联调、对象存储、生产部署 |

## 2. 开发原则

1. **契约先行**：先改 `contracts/p0-api.yaml`，再写 serializer/service/view；已实现接口用 `make schema` 生成快照。
2. **资金优先**：记账、对账、退款、结算先于运营页面；任何余额变更只能走 `post_transaction`。
3. **状态机唯一入口**：订单状态只能走 `transit_order`，非法迁移返回 409。
4. **未定项不写死**：短信服务商、提现手续费、数据留存期限标 TBD，用适配层或配置隔离。
5. **每个里程碑有端到端验收**：API 级 E2E + 资金对账通过，才算完成。

## 3. 里程碑

### M0 · 工程基线（基本完成）

- 已完成：项目骨架、38 张表、记账与状态机、JWT、平台后台、契约、CI/门禁。
- 收尾：GitHub 远程仓库与 CI 首次运行；MySQL 8 本地一致性验证（可并入 M5）。
- 出口标准：`make verify` 全绿；`make audit` 0 差异；契约检查通过。

### M1 · 可下单、可支付（Mock 微信）

**目标**：跑通「登录 → 地址 → 购物车 → 下单 → 支付回调 → 待接单」的 API 闭环。

- 认证：微信登录适配层（先用 mock code）、H5 短信适配层（先 FakeProvider）、JWT 签发。
- 地址簿：新增/修改/删除/列表/默认地址。
- 购物车：加购、改数量、选中、删除；单店约束。
- 下单：服务端定价、库存锁定、时段预占、幂等键、佣金解析与快照。
- 支付：创建支付单、Mock 统一下单、支付回调（验签占位 + 金额校验 + 幂等记账）。
- 取消：待支付超时关闭、待接单取消退款占位。
- 核销码生成、订单详情与时间轴。
- 测试：重复下单、库存冲突、回调重放、金额不一致、跨用户越权。

**出口标准**：API 级 E2E 跑通全链路；支付成功记账借贷平衡；重复请求不重复记账。

> 进度：认证、地址、购物车、下单、库存/时段预占、Mock 支付与回调、取消已完成；真实微信支付留到 M5。

### M2 · 履约、售后与退款

**目标**：覆盖订单状态机全部分支，售后能冻结结算项并产生退款分录。

- 商户端：接单、拒单、发货/备货、核销、售后同意/拒绝。
- 消费者端：确认收货、预约、评价、售后申请与进度。
- 退款：退款单状态机、微信退款 Mock、结算前/结算后退款分录、负余额处理。
- 仲裁：超时转仲裁、平台裁定、责任归属与执行退款。
- 测试：状态迁移矩阵、退款额度上限、冻结/解冻、部分退款尾差。

> 进度：接单/发货/核销、确认收货、评价、售后与退款、超时转仲裁（`escalate_after_sales`）、平台裁定已完成；已结算订单退款留到 M3，真实微信退款留到 M5。

**出口标准**：订单状态机全部合法迁移有测试；退款后 `audit_ledger` 仍为 0 差异。

### M3 · 资金与结算闭环

**目标**：订单完成 → 结算项 → 批次 → 发布入账 → 提现 → 人工网银打款/驳回。

- 结算：批次生成、到期校验、发布记账、结算项状态流转。
- 提现：申请、审核、打款回填回单、驳回退回；余额与分录一致。
- 平台：支付配置读写、冻结结算、对账结果、操作日志、规则版本。
- 商户：账户余额、账单与流水。
- 定时任务：超时关单、售后超时转仲裁、结算批次扫描、Outbox 发送。
- 测试：结算周期 N、重复发布幂等、提现余额不足、打款/驳回反向分录。

> 进度：结算批次生成/发布、提现申请/打款/驳回、冻结结算、对账结果、操作日志、规则版本、支付配置、账户余额与账单、已结算订单退款、超时关单与结算批次扫描已完成；Outbox 发送留到 M5。

**出口标准**：模拟一天业务后，四本账对账 0 差异；`make audit` 纳入日终任务。

### M4 · 三端前端

**目标**：消费者小程序/H5、商户中心（同一小程序内菜单）、平台 PC 可操作 P0 流程。

- 契约消费：由 `p0-api.yaml` 生成 TypeScript 类型与请求客户端，禁止手写重复模型。
- 消费者：门店/商品、购物车、下单支付、订单详情、售后。
- 商户中心：个人中心菜单入口、商品发布、订单处理、核销、账单、提现。
- 平台 PC：审核、订单查询、仲裁、结算发布、提现打款、支付配置、对账、日志。
- Mock 策略：后端未就绪时用契约 Mock Server，前端不阻塞。
- 出口标准：三端按 P0 主流程完成 UAT；关键操作有权限与数据隔离验证。

> 进度：契约类型由 `p0-api.yaml` 生成（`frontend/shared/schema.d.ts`）；平台 PC（Vue 3 + Vite）与消费者/商户中心（Taro + React）已完成 P0 主流程页面，均已构建通过。已对照交互原型补齐：门店首页（搜索/类目/距离）、门店详情、商品规则与预约时段、地址簿、订单进度与核销凭证、评价、我的菜单；平台端待办队列、仲裁详情与举证、规则配置、商户管理（创建/状态筛选/详情/停业恢复封禁）与审核中心（商户入驻审核联动商户状态）；商户中心商品管理（多 SKU 发布、编辑重审、上下架、商户货号、本店分类）与后台商品审核；平台两级商品类目维护与商户自有分类隔离；平台商品管理（编辑商户商品直接生效、违规下架/恢复）、商品模板（指定商户或全商户分发、商户认领上下架、手动同步）、素材库（一级文件夹、图片/视频上传、素材选择器、外部 URL 拦截）；H5 商户端平台商品认领页与平台下架原因提示。浏览器端到端 UAT 已通过：平台后台登录与订单列表；消费者门店→商品→立即购买→Mock 支付→订单进度；商户登录→接单→待履约；平台端可见该订单；平台端商户停业/恢复与入驻审核通过；商户发布商品→后台审核通过→消费者门店可见；素材上传→模板发布→商户认领→平台编辑→违规下架→恢复→手动同步全链路。真实微信登录与正式 UAT 留到 M5。

### M5 · 真实渠道与上线准备

**目标**：从 Mock 切换到真实微信支付、短信、MySQL 与生产部署。

- 微信支付 V3：商户号/证书配置、统一下单、回调验签、退款、账单下载。
- 短信：选定服务商，替换 `SmsProvider` 适配器。
- 基础设施：MySQL 8 集成测试、Redis、对象存储、HTTPS 域名、备份与恢复演练。
- 安全：敏感字段密钥管理、权限矩阵复核、支付配置访问审计、限流。
- 可观测：traceId、结构化日志、资金异常告警、对账告警。
- 压测：下单/支付回调/核销峰值；重复回调与并发扣减。
- 出口标准：staging UAT 通过；上线检查表（回滚、备份、对账、告警）全部签字。

### M6 · P1 扩展（不在 P0 范围）

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 微信商户号/证书未到位 | 无法真实支付 | 先 Mock，接口按 V3 契约实现；证书只在后台配置表 |
| 短信服务商未定 | H5 登录受阻 | FakeProvider + 统一 SmsProvider 接口，最后替换 |
| 提现手续费率未定 | 提现金额展示与协议 | 配置项预留，未配置时不计费并在协议标注 TBD |
| 数据留存期限未定 | 合规风险 | 加密先落地；留存策略等法务必确认，不做自动删除 |
| SQLite 与 MySQL 差异 | 约束/排序/时区问题 | M5 必跑 MySQL 8 集成测试；CI 增加 MySQL job |
| 结算后退款负余额 | 商户欠款处理 | 允许 available 为负，后续结算抵扣；禁止直接抹平 |
| 并发扣库存/核销 | 超卖、重复核销 | 条件更新 + 唯一约束 + 幂等键，不依赖应用锁 |
| 契约与实现漂移 | 前后端返工 | 契约先行 + CI `contract-check` + 生成快照 diff |
